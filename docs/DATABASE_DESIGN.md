# DATABASE_DESIGN.md — CineMind AI

This is a **design proposal only** — no tables are created yet (per project rules). Actual creation happens via SQLAlchemy models + Alembic migrations at Milestone 3.

## Entity Overview & Relationships

```
users ───────< ratings >──────── movies ───────< movie_genres >──────── genres
  │                                  │
  │                                  ├──< reviews (also references users)
  ├──< watchlist >───────────────────┤
  ├──< watch_history >───────────────┤
  ├──1─ user_preferences             │
  └──< recommendation_results >──────┘
```

- One user has many ratings, reviews, watchlist entries, watch_history entries, recommendation_results.
- One movie has many ratings, reviews, and many-to-many genres via `movie_genres`.
- `user_preferences` is effectively 1:1 with `users` (the "Movie DNA" profile, populated starting V2).
- `recommendation_results` is a cache table (user × recommended movie × score × reason), regenerated periodically rather than computed live on every request.

## Entities & Important Fields

### users
- `id` (PK)
- `email` (unique, indexed)
- `hashed_password`
- `display_name`
- `created_at`
- Notes: never store plaintext passwords; email uniqueness enforced at DB level, not just app level.

### movies
- `id` (PK)
- `tmdb_id` (unique, indexed) — link back to source of truth
- `title`
- `overview`
- `release_date`
- `runtime`
- `poster_path`
- `original_language`
- `popularity`, `vote_average`, `vote_count` (cached from TMDB, refreshed periodically)
- `overview_embedding` (vector, added in V2 for semantic search — nullable until backfilled)
- Notes: movies are a **cache** of TMDB data, not manually entered; `tmdb_id` is the natural external key.

### genres
- `id` (PK)
- `tmdb_genre_id` (unique) — TMDB has a fixed genre list
- `name`

### movie_genres (join table)
- `movie_id` (FK → movies)
- `genre_id` (FK → genres)
- Composite PK on (`movie_id`, `genre_id`)

### ratings
- `id` (PK)
- `user_id` (FK → users)
- `movie_id` (FK → movies)
- `score` (1–5, constrained)
- `created_at`, `updated_at`
- Unique constraint on (`user_id`, `movie_id`) — one rating per user per movie, updatable.

### reviews
- `id` (PK)
- `user_id` (FK → users)
- `movie_id` (FK → movies)
- `content` (text)
- `created_at`, `updated_at`
- V2+ analysis fields (nullable until NLP pipeline runs): `sentiment_label`, `sentiment_score`, `contains_spoiler` (bool), `credibility_score`
- Notes: keep raw `content` immutable-ish (edits create `updated_at` change); NLP fields are derived and can be recomputed without touching the source text.

### watchlist
- `id` (PK)
- `user_id` (FK → users)
- `movie_id` (FK → movies)
- `added_at`
- Unique constraint on (`user_id`, `movie_id`).

### watch_history
- `id` (PK)
- `user_id` (FK → users)
- `movie_id` (FK → movies)
- `watched_at`
- Notes: distinct from `ratings`/`watchlist` — tracks actual (self-reported) viewing, useful signal for collaborative filtering later even without an explicit rating.

### user_preferences ("Movie DNA", V2+)
- `user_id` (PK, FK → users)
- `preference_vector` (vector or JSON — derived taste representation)
- `top_genres` (JSON/array, denormalized for fast display)
- `updated_at`
- Notes: recomputed periodically (batch job) from ratings + reviews + watch_history, not maintained transactionally.

### recommendation_results
- `id` (PK)
- `user_id` (FK → users)
- `movie_id` (FK → movies)
- `score` (float)
- `reason` (text/JSON — explanation payload for explainable recommendations)
- `algorithm` (string — e.g. `content_based`, `collaborative`, `hybrid`, so results are traceable to the method that produced them)
- `generated_at`
- Notes: acts as a cache so recommendation endpoints can serve fast reads; regenerated by a batch/background job rather than computed synchronously per request once V2's heavier models are in play.

## Design Notes
- Foreign keys use standard cascade rules to be finalized at implementation (e.g., deleting a user should cascade-delete their ratings/reviews/watchlist, but this needs explicit confirmation before implementing, per Development Rules).
- Vector columns (`overview_embedding`, `preference_vector`) are deferred until the `pgvector` extension is introduced at the semantic-search milestone (V2) — MVP schema does not require them.
- All `*_at` timestamp columns use UTC.
